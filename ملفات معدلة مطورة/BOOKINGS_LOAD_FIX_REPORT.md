# 📊 تقرير: إصلاح مشكلة سحب المواعيد الكامل (Bookings Overfetch)
## من "تحميل كل التاريخ في كل مرة" إلى "تحميل اليوم فقط"

---

## 1. المشكلة بالأرقام — لماذا هذا "ملحّ" بالفعل

لنفترض عيادة متوسطة النشاط:
- 40 موعد/يوم × 300 يوم عمل/سنة = **12,000 موعد/سنة**
- بعد سنتين من التشغيل = **24,000 سجل** في `/bookings`
- حجم السجل الواحد تقريباً (patName, patPhone, date, time, status, docKey, docName, fee, notes...) ≈ **400 بايت**

### الوضع الحالي (بدون فلترة):
```
كل فتحة لـ emr.html أو dashboard.html
  → .on('child_added') على /bookings كاملاً
  → يسحب 24,000 سجل × 400 بايت ≈ 9.6 ميجابايت

5 موظفين × 10 مرات فتح/يوم = 50 فتحة/يوم
  → 50 × 9.6 MB ≈ 480 MB/يوم
  → ≈ 14.4 GB/شهر  لعيادة واحدة فقط!
```

> ⚠️ هذا يتجاوز حد Firebase Spark المجاني (10GB/شهر) **بمفرده، لعيادة واحدة**.
> لو كان لديك 50 عيادة بهذا النشاط → **720 GB/شهر**.

### بعد التطبيق (مُفلتر بالتاريخ + أرشفة):
```
/bookings يحتوي فقط على: اليوم + المواعيد المستقبلية المجدولة
  ≈ 40-80 سجل × 400 بايت ≈ 32 كيلوبايت

50 فتحة/يوم × 32 KB ≈ 1.6 MB/يوم
  → ≈ 48 MB/شهر لكل عيادة
```

**النتيجة: تقليل الاستهلاك بنسبة ≈ 99.7%** — ومن 14.4GB إلى 48MB شهرياً لكل عيادة.

## 2. كيف يعمل الحل (شرح معماري)

### أ) الاستعلام المُحدَّد بالتاريخ (Scoped Query)
```javascript
// قبل ❌ — يسحب كل تاريخ العيادة:
db.ref(BASE + '/bookings').on('child_added', ...)

// بعد ✅ — يسحب فقط اليوم فصاعداً:
db.ref(BASE + '/bookings')
  .orderByChild('date')
  .startAt(todayStr)
  .on('child_added', ...)
```
بما أن حقل `date` بصيغة `YYYY-MM-DD` (مُستخدَم فعلاً في الكود الحالي عبر
`toLocaleDateString('en-CA')`)، فإن الترتيب الأبجدي = الترتيب الزمني تماماً.
لذلك `startAt('2026-06-14')` يُعيد فقط مواعيد اليوم وما بعده.

### ب) محرك الأرشفة التلقائي (`argon-booking-archiver.js`)
يعمل بآلية **"امسح مرة، انقل، توقف"** — وليس مستمعاً لحظياً:

```
كل 6 ساعات (لكل متصفح، عبر localStorage):
  1. .once('value') على /bookings  ← قراءة واحدة فقط
  2. لكل حجز: هل status ∈ {done, completed, cancelled, no_show}؟
     أو هل date < (اليوم - 2 يوم) [حجز قديم لم يُعالَج]؟
  3. إن كان أحدهما صحيحاً → نقل لـ /archived_bookings
     عبر update() واحدة (atomic — نقل لا حذف منفصل)
  4. /bookings يبقى صغيراً دائماً
```

**القفل الموزّع**: قبل التشغيل، يكتب جهاز قفلاً مؤقتاً (5 دقائق) في
`_meta/archiver_lock`، فلا يحدث تعارض إذا فتح طبيبان النظام في نفس
اللحظة على جهازين مختلفين.

### ج) الأرشيف نفسه — مسطّح ومفهرس، لا تحميل كامل أبداً
```javascript
/archived_bookings/{bookingId}
  .indexOn: ["date", "status", "doctorId", "patientId"]
```
يُستعلَم عنه **فقط** بـ:
```javascript
db.ref(`${BASE}/archived_bookings`)
  .orderByChild('patientId')
  .equalTo(patientId)   // لسحب تاريخ مريض معيّن فقط
  .once('value')
```
لن يُستخدَم `.on('value')` أو `.once('value')` على الأرشيف بالكامل أبداً —
فقط استعلامات مفهرسة محدودة.

## 3. التأثير على الميزات الحالية (Side Effects — مهم تقرأه)

| الميزة | السلوك القديم | السلوك الجديد |
|---|---|---|
| غرفة الانتظار (Waiting Room) | كل الحجوزات (حتى من سنوات) | اليوم فقط ✅ (هذا هو المطلوب أصلاً) |
| جدول مواعيد الطبيب (Calendar) | كل الحجوزات تاريخياً (كانت مشكلة!) | اليوم + المستقبل ✅ |
| عزل المرضى حسب الطبيب (Complex Mode) | يعتمد جزئياً على `_liveBookings` | **غير متأثر** — `hasPastVisit` يعتمد على `patient.visits` لا على `_liveBookings` |
| فتح مريض من حجز قديم (`openPatientFromBooking`) | يعمل لأي حجز قديم في الذاكرة | يعمل فقط للحجوزات النشطة (اليوم+) — الحجوزات المؤرشفة لا تُفتح تلقائياً، لكن **ملف المريض نفسه غير متأثر** ويظهر بكامل تاريخه |
| حجز "منسي" (status=waiting من قبل يومين) | يبقى يظهر للأبد في الذاكرة | يُؤرشف تلقائياً بعد 2 أيام (`staleAfterDays`)، يختفي من غرفة الانتظار |

> **ملاحظة مهمة**: تاريخ المريض الطبي (`patients/{uid}/visits`) **لم يتأثر إطلاقاً** —
> هذا الإصلاح يخص فقط جدول **الحجوزات/المواعيد** (`/bookings`)، وهو نظام
> منفصل تماماً عن السجل الطبي للمريض.

## 4. ملف dashboard.html — يحتاج نفس المعالجة

لم يُرفَق كود `dashboard.html` في هذا التقرير، لكن بناءً على الوصف
("`db.ref(BASE + '/bookings').on('value', ...)`")، فإنه يستخدم نمطاً
أخطر من EMR: `.on('value')` على الجذر بالكامل (لا `child_added`)
— أي يُعاد تحميل **كل** المواعيد دفعة واحدة عند **أي** تغيير على **أي** حجز.

### التعديل المطلوب (نفس المبدأ):
```javascript
// ❌ القديم:
db.ref(BASE + '/bookings').on('value', snap => {
  const allBookings = snap.val() || {};
  // ... رسم كل شيء من جديد كل مرة
});

// ✅ الجديد:
const todayStr = new Date().toLocaleDateString('en-CA');
db.ref(BASE + '/bookings')
  .orderByChild('date')
  .startAt(todayStr)
  .on('value', snap => {
    const todaysBookings = snap.val() || {};
    // الآن فقط اليوم+ — حجم صغير دائماً
  });
```

**أضف أيضاً** في dashboard.html:
```html
<script src="argon-booking-archiver.js"></script>
```
وفي التهيئة:
```javascript
ArgonBookingArchiver.init(db, BASE, CID);
ArgonBookingArchiver.runIfDue();
```

> 📩 إذا رفعت كود `dashboard.html`، يمكنني إعطاءك الـ patch الدقيق
> سطراً بسطر بنفس أسلوب الملفات الأخرى.

## 5. ملفات أخرى يُحتمل أن بها النمط نفسه (تحقّق منها)

بناءً على بنية النظام، هذه الملفات **قد تحتوي** على `.on('value')`
مشابه على `/bookings` أو مسارات كبيرة أخرى — راجعها بنفس المبدأ:

- `pharmacy.html` / `pharmacy-app.js` — قد تستمع لـ `/prescriptions` كاملة
- `lab.html` / `lab-app.js` — قد تستمع لـ `/lab_orders` كاملة
- `radiology.html` — قد تستمع لـ `/radiology_orders` كاملة
- `index.html` (بوابة الحجز) — قد تجلب `/doctors` أو `/bookings` لعرض الأوقات المحجوزة

**القاعدة العامة لأي مسار يكبر بمرور الزمن** (المواعيد، الفواتير، السجلات):
> لا تستمع لجذر كامل بدون `.orderByChild().startAt()` أو `.limitToLast()`.
> أرشِف أي شيء "منتهي" إلى مسار منفصل مفهرس.

نفس نموذج `ArgonBookingArchiver` يمكن تعميمه على `/invoices` و
`/prescriptions` و `/lab_orders` لاحقاً بنفس الطريقة بالضبط — فقط
بتغيير اسم المسار وحقل التاريخ.

## 6. خطة Blaze — متى ولماذا

| | Spark (مجاني) | Blaze (دفع حسب الاستخدام) |
|---|---|---|
| اتصالات متزامنة | 100 | 200,000 |
| Bandwidth شهري | 10 GB | غير محدود (يُحاسَب) |
| التكلفة إذا بقيت ضمن نفس الاستهلاك | $0 | **$0 أيضاً** (أول 10GB مجاني حتى في Blaze) |

**الخلاصة**: الترقية لـ Blaze لا تكلّف شيئاً إذا بقي الاستهلاك ضمن
النطاق المجاني — فقط تُزيل **القيد الصلب** (Hard Cap) الذي يوقف
الخدمة كاملة عند 100 اتصال متزامن أو 10GB. **يُنصَح بالترقية الآن**
كإجراء وقائي بحت، بالتوازي مع تطبيق إصلاحات هذا التقرير (التي تقلل
الاستهلاك الفعلي 99%+ بحيث لا تقترب من أي حد أصلاً).

## 8. خطوات التطبيق السريعة

1. انشر `firebase.rules.json` المحدَّث (يحتوي الآن `archived_bookings` + `_meta`)
2. أضف `<script src="argon-booking-archiver.js"></script>` في `emr.html`
   (وفي `dashboard.html` لاحقاً)
3. في `initEMR()`: أضف `ArgonBookingArchiver.init(...)` و `runIfDue()`
4. استبدل قسم استماع `/bookings` بالنسخة المُحدَّدة بالتاريخ
   (من `emr-bookings-patches.js`، STEP 1)
5. عدّل `completeWorkspaceVisit()` لاستخدام `archived_bookings`
   بدل `completedBookings` (STEP 2)
6. (اختياري) فعّل لوحة الإدارة `renderArchiverAdminPanel()` لمتابعة
   الإحصائيات والتشغيل اليدوي

**أول تشغيل سيؤرشف فوراً كل الحجوزات القديمة المتراكمة** — توقع
رسالة في الـ console مثل:
```
📦 ARGON Archiver: تمت أرشفة 23,847 حجزاً (من إجمالي 24,012 في /bookings)
```
